# Monitoring Agents

Agents are the distributed workers that execute health checks across your infrastructure. Each agent runs as a lightweight process (typically in Docker) and reports check results back to the LuxSwirl server. The Agents page provides the approval workflow, performance monitoring, and configuration management for all agents.

**Access:** **Agents** in the sidebar, or `/agents`.

______________________________________________________________________

## Agent lifecycle

### Registration

When an agent first starts, it attempts to register with the server using a **registration key** (set via the `LUXSWIRL_AUTH_KEY` environment variable):

1. The agent starts and sends a registration request to the server.
1. The server creates an agent record with `pending` approval status.
1. The agent appears in the **Pending Approval** section.
1. An administrator approves or rejects the agent.
1. On approval, the server generates a unique API key for the agent.
1. The agent receives the API key and stores it encrypted locally.
1. The agent begins executing checks and sending results.

Two distinct keys are involved:

- **Registration key** — a shared secret used only for initial registration (set in `.env` or docker compose).
- **API key** — a unique per-agent key for ongoing authentication, generated by the server on approval.

### Approval states

| State        | Description                | Behavior                                                       |
| ------------ | -------------------------- | -------------------------------------------------------------- |
| **Pending**  | Waiting for admin approval | Cannot execute checks; shown in the pending section at the top |
| **Active**   | Approved and operational   | Executes checks and reports results normally                   |
| **Paused**   | Temporarily suspended      | Continues running but does not execute checks                  |
| **Disabled** | Stopped until enabled      | Does not execute checks; still listed                          |
| **Archived** | Out of use, kept           | Does not execute checks; hidden from lists; history kept       |
| **Rejected** | Denied access              | Cannot communicate with the server                             |

### Online / offline status

An agent is considered **online** if it has sent a heartbeat within the configured threshold (default 5 minutes). A pulsing green dot means online; a red dot means offline. The heartbeat mechanism:

- Agents send periodic heartbeat messages to the server.
- Each heartbeat includes agent metadata (CPU, memory, queue depth, etc.).
- Default interval is 60 seconds (configurable per agent).
- The server sets `last_seen` to its own clock when the heartbeat arrives (never the time the agent claims), so a skewed agent clock cannot keep an agent online; once `last_seen` is older than the threshold, the agent is marked offline.
- Only the agent's own key updates the agent; a pending agent proves itself with the recovery secret it was given at registration, and that updates only the pending agent (an agent build that sends no secret is still checked against the registration key, and the server logs a warning to upgrade it). An approved agent that has not stored its key yet may heartbeat with its recovery secret: the server tells it to recover its key and records nothing.

**Heartbeat vs check sync** — the *heartbeat* is how often the agent sends a health/metadata update; the *check sync* is how often the agent re-fetches its checks even when nothing announced a change. A change to the agent's checks reaches it at its next heartbeat either way; the check sync is the backstop, checked at each heartbeat, so it is never sooner than the heartbeat interval.

## Pending Approval section

This section appears at the top of the Agents page whenever one or more agents await approval (it stays pinned at the top). Each pending agent card shows:

- **Agent name** — usually derived from the hostname.
- **First Seen** — timestamp of the initial registration request.
- **Hostname** — server hostname, if provided.
- **IP Address** — source IP of the registration request.
- **Version** — agent software version (e.g. `1.0.15`).

**Approval actions:**

- **Approve** (green, one-click, no confirmation) — moves the agent to the active list, generates and sends its unique API key, and the agent begins executing assigned checks.
- **Reject** (red, two-click confirmation) — marks the agent `rejected`; it cannot re-register without a server restart. The two-click requirement prevents accidental rejection.

**Why manual approval?** It prevents unauthorized agents from joining your monitoring infrastructure, lets you review the agent's source (hostname, IP) before trusting it, and protects against rogue agents flooding the server with fake data.

## Active agents list

Shows all approved agents, paginated, with rich performance metrics. Two controls sit at the top:

- **Metrics time range** (1 Hour / 4 Hours / 8 Hours / 24 Hours, default 4h) — sets the window for the CPU/Memory/Checks sparklines (not the stats grid).
- **Active Only** checkbox — when checked, hides offline agents.

### Card header

- **Status indicator** — pulsing green dot (online) or red dot (offline); a yellow border warns if the agent has been offline longer than the threshold.
- **Agent name** — links to the agent detail page.
- **Status badge** — Active, Paused, Disabled or Archived.
- **Tags** — agent-level tags (e.g. `production`, `us-east-1`), inherited by all checks on the agent. Tags are admin-managed: the tags an agent declares are kept only while it is pending, as a suggestion for approval; after approval only an admin changes them (**Edit**), and a tag change takes effect on the agent's next check sync. An agent has at most 100 tags, each at most 100 characters.
- **Metadata row** — hostname (monospace), heartbeat interval, and check-sync interval.

### Action buttons

| Button              | Action                                                                                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Reload**          | Forces the agent to immediately pull the latest check configurations instead of waiting for the next sync — use after adding/modifying checks                                           |
| **Edit**            | Opens a panel to edit the agent name, tags, heartbeat interval, check-sync interval, and custom metadata (JSON); no restart required                                                    |
| **Import / Export** | Bulk check management — export all of this agent's checks as JSON, or import JSON to bulk-create checks (handy for cloning config across agents). See [Import/Export](import-export.md) |
| **View Checks**     | Navigates to the Dashboard filtered to this agent                                                                                                                                       |

A yellow **N dead-lettered** badge next to the approval status means the server refused N report batches as invalid (its own 400 or 422 error, for example a report envelope an older server does not accept). A single result the server cannot store does not do this: it is skipped and the rest of the batch is kept. A 400 from a proxy, or the server's `Invalid host header` answer to a misaddressed agent, is not a refusal either: those batches stay pending and are sent once the address is fixed. A batch larger than a proxy's body limit (413) is sent in smaller parts instead. The agent keeps them in its local `dead_letters` table instead of retrying them, so they never hold up the rest of its backlog. The badge is absent when the count is zero or the agent does not report it.

### Agent changes that affect a synthetic check

A synthetic check runs a script on the agent's host, so an agent change that moves or removes one needs an admin. An editor can't rename or retag an agent into or out of a synthetic check's selector, approve an agent that one already matches, or delete an agent that owns one; every other agent change stays an editor's.

### Deleting an agent

**Delete** is at the bottom of the agent's **Edit** panel. Deleting removes the agent, every check it owns and their stored results, plus any results it reported for other agents' checks, and it cannot be undone. Clicking **Delete** shows how many checks and stored results go with it, then asks for the agent's name (its hostname if it has no name); the delete runs only when the typed name matches. To stop an agent while keeping its checks and history, **Pause**, **Disable** or **Archive** it instead.

### Archiving an agent

**Archive** (in the agent's **Edit** panel, for an active, paused or disabled agent) puts an agent out of use without deleting anything:

- the server refuses it, so it runs no checks, reports nothing and raises no alerts;
- it leaves the agent list, the agent pickers and the dashboard filters, and the dashboard no longer shows the checks pinned to it (a replicate or distribute check stays, since it runs on its other agents);
- the agent, its checks and their stored results are kept.

The stale-agent cleanup never deletes an archived agent, and `/metrics` stops exporting it. Tick **Archived** above the agent list to see the archived agents. **Restore** is the only way out of Archived: it makes the agent **Disabled**, so it runs nothing until you **Enable** it.

Each action applies only from the states it is offered in: Approve a pending or rejected agent, Reject a pending one, Pause an active one, Resume a paused one, Disable an active or paused one, Enable a disabled one.

### Statistics grid

| Stat                 | Meaning                                                                                                                                 | Healthy / warning                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **Success Rate**     | Overall success rate for recent checks (from agent metadata, updated each heartbeat)                                                    | Green ≥99%, yellow 95–99%, red \<95%                                      |
| **Checks**           | `enabled/total` (e.g. `47/52` = 47 enabled of 52 total)                                                                                 | —                                                                         |
| **Uptime**           | Agent **process** uptime (since registration or last restart), humanized (`5h`, `3d`) — not check uptime                                | —                                                                         |
| **Queue Depth**      | Check results waiting to be sent to the server                                                                                          | 0 = healthy (sent immediately); >100 = heavy load or network issues       |
| **Reporter Backlog** | Count of report files stored on disk because the server was unreachable, with the age of the oldest; replayed when connectivity resumes | 0 = healthy; >0 = the server was unreachable at some point (yellow alert) |
| **API Key Status**   | Status (green dot + "Active"), created date, and last-used time ("Never Used" in orange if the agent hasn't authenticated yet)          | —                                                                         |

The API Key card also has **View Key** (shows a truncated key hash for verification), **Regenerate** (invalidates the old key and keeps the recovery secret; the agent then recovers a key of its own), and **Revoke** (invalidates the key and voids the recovery secret; that install registers again as a new pending agent for an admin to approve). See [Managing agent API keys](#managing-agent-api-keys). The full API key is never displayed — only the agent holds the complete key, stored encrypted on disk; the UI shows a hash for verification only.

### Performance sparklines

Three mini-charts over the selected Metrics range give a quick health read without opening the detail page: **CPU usage** (0–100%), **Memory usage** (0–100%), and **Checks executed** (activity level). Flat lines indicate stable performance; spikes indicate potential issues.

### Agent information

A metadata grid at the bottom of the card: IP address, version, platform (OS), Python version, hostname (FQDN), uptime, heartbeat/sync intervals, tags, and created date.

## Agent detail page

Open it by clicking an agent's name. A breadcrumb, the agent name, hostname, and a large online/offline badge head the page. A **time range** selector (1 Hour / 4 Hours / 8 Hours / 24 Hours / 3 Days / 7 Days, default 4h) drives all charts and metrics.

### Statistics cards

| Card                 | Detail                                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Total Checks**     | Check executions in the last 24h (e.g. `1,440` for one check per minute)                                                                               |
| **Success Rate**     | Success % over 24h, with `passed/total` (e.g. `1,425/1,440 passed`); green ≥99%, yellow ≥95%, red \<95%                                                |
| **Average Latency**  | Mean response time across all checks (e.g. `87ms`)                                                                                                     |
| **Uptime**           | Humanized (`5h`, `12d`), with the registration date                                                                                                    |
| **File Descriptors** | Open FDs and "X% of limit"; **yellow at ≥80%** of the OS limit — catches FD leaks or misconfiguration                                                  |
| **Subprocesses**     | Child processes spawned; normal 0–10, elevated 10–50 (synthetic checks spawn browser processes via Playwright), concerning >50 (possible process leak) |

### Performance charts

Six Chart.js time-series charts (one data point per minute; hover for exact values; X-axis is time):

| Chart                           | Reads                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------ |
| **CPU Usage** (0–100%)          | Sustained high usage indicates check-load issues                               |
| **Memory Usage** (0–100%)       | Typically 10–30%; steady growth indicates a memory leak                        |
| **Queue Depth**                 | Should stay at/near 0; sustained elevation = network issues or server overload |
| **Checks Executed / Succeeded** | Two lines (executed vs succeeded); the gap between them is failures            |
| **File Descriptors**            | Stable or slow growth is healthy; rapid growth indicates a leak                |
| **Subprocesses**                | Should correlate with synthetic checks executing                               |

(Charts don't support zoom — change the time-range selector instead; right-click to save a chart as an image.)

### Agent information and assigned checks

A detailed metadata grid lists IP address, version (semver), platform (e.g. `Linux 5.15.0-91-generic`), Python version, hostname, exact uptime in seconds, heartbeat and check-sync intervals, tags, created timestamp, and last-seen timestamp.

The **Assigned Checks** table lists every check on the agent — Check Name (links to detail), Type, Target, Interval, Enabled (inline toggle), and Last Check (relative time).

## Common workflows

### Approving a new agent

1. The new agent appears in **Pending Approval** at the top of the page.
1. Review its information: hostname, IP, version.
1. Verify it's an expected agent (not rogue/unauthorized).
1. Click the green **Approve** button.
1. The agent immediately begins executing assigned checks and moves to the active list.

### Monitoring agent health

1. On the **Agents** page, scan cards for red (offline) indicators.
1. Check **Reporter Backlog** — yellow warning if >0.
1. Check **Success Rate** — red if \<95%.
1. Click an agent name to open the detail page and review the charts for anomalies: CPU/memory spikes (check-load issues), queue-depth elevation (network/server issues), file-descriptor growth (resource leak).

### Forcing a check-configuration reload

1. After creating/modifying checks on an agent, click **Reload** on the agent card.
1. Wait 5–10 seconds for the reload to complete.
1. Click **View Checks** to verify the new checks appear and are executing (latency values populate).

### Troubleshooting an offline agent

1. Check the **last seen** timestamp — how long has it been offline?
1. Review **reporter backlog** — did it go offline and come back? (backlog processing)
1. SSH to the agent host and check the process and logs:
   ```bash
   docker ps | grep luxswirl_agent
   docker logs luxswirl_agent --tail 50
   ```
1. Check network connectivity to the server:
   ```bash
   docker exec luxswirl_agent curl -I https://server.example.com:9000/health
   ```
1. Verify the API key — if stale/revoked, **Regenerate** it in the agent card's API Key section. At its next heartbeat the agent finds its old key refused and recovers the new one itself, with its recovery secret and the registration key (`LUXSWIRL_AUTH_KEY`); that registration key must still be active.

### Cloning checks across multiple agents

1. Open the agent with the existing checks.
1. Click **Import/Export** → **Export Checks** → select checks (or Select All) → **Download JSON**.
1. Open the target agent → **Import/Export** → **Import Checks** → upload the JSON.
1. Review the imported checks and click **Import X Checks** — they're created and begin executing immediately.

### Investigating performance issues

1. Open the agent detail page and set the range to **24 Hours** or **3 Days**.
1. **CPU Usage** — look for sustained high usage.
1. **Memory Usage** — look for a memory leak (steady growth).
1. **Queue Depth** — spikes indicate throughput issues.
1. **Checks Executed/Succeeded** — a large gap indicates failures.
1. **File Descriptors** — growth indicates a leak.
1. **Subprocesses** — spikes from synthetic checks.

### Managing agent API keys

- **View key (hash only):** API Key card → **View Key** shows the key hash and metadata; use the hash to verify it matches the agent's stored key.
- **Regenerate:** **Regenerate** → confirm. The old key stops working at once; the agent keeps its recovery secret. The new key is never sent to the agent. While the server accepts its key, the agent's heartbeat carries the key alone, and its recovery secret never leaves it. At its next heartbeat the server refuses the old key with its JSON 401; the agent then sends its recovery secret beside the key, the server answers that it no longer accepts the key (`agent_key_accepted: false`), and the agent fetches a fresh key from `recover-key` with the registration key and that secret. (A 401 that is not the server's own, say a proxy's page, never makes the agent send its secret or give up its key.) It saves the fresh key to its encrypted credentials file, uses it from then on and stops sending the secret, so the key shown after **Regenerate** is replaced by the one the agent fetched: nothing needs configuring, and the shown key never goes in `LUXSWIRL_AUTH_KEY`, which holds the registration key. This needs the agent's registration key (`LUXSWIRL_AUTH_KEY`) to still be active; the old key stays in the file until the new one is saved (each save replaces the file whole or not at all), so a restart before then takes the same path. Key recovery shares the registration rate limit (`security.registration_rate_limit`, per client address, every recovery counted): when many agents behind one address need a key at once, the ones past the limit retry about once a minute until it allows them. The refused heartbeat counts against the agent's pending budget (5 an hour per address and agent), so does a refused credential anyone else at the agent's address sends with its id: on a shared network they can hold its recovery back for up to an hour. Until it holds a key the server accepts, the agent's Docker health check reads unhealthy. Two running copies of one agent (a cloned host with the same credentials) take the key from each other; the agent then waits longer between recoveries, up to an hour, and logs that another copy may be using its key.
- **Revoke:** **Revoke** → confirm. The key stops working, and the agent's recovery secret is voided with it, so that install can never recover a key, and neither can any copy of its credentials or a captured heartbeat. At its next heartbeats the server refuses the key, then the secret; the agent asks `recover-key` once, is refused there too, and registers again with its registration key as a new pending agent, which an admin must approve (or reject). The old agent stays listed with no key: delete it once the new one is approved. A registration that fails (no active registration key) keeps the old credentials and is tried again at the first heartbeat five minutes later. Only a refusal the server marks as its own (header `X-LuxSwirl-Refused`) starts this: a gateway's or proxy's 401 never makes the agent register again. To rotate a key and keep the agent, **Regenerate** instead; to stop an agent, **Disable** or **Archive** it.

## Performance considerations

**High agent count (100+):**

- Use the **Active Only** filter to focus on online agents.
- Increase the per-page setting to reduce pagination.
- Consider a longer heartbeat interval to reduce database writes (default 60s).
- Use tags to organize agents by environment/datacenter.

**High check count per agent (500+):**

- Watch **Queue Depth** — sustained elevation indicates agent overload.
- Increase `max_concurrent_checks` in the agent configuration (default 200).
- Consider splitting checks across multiple agents.
- Review intervals — does everything need to run every 60s?

**Resource-monitoring alert thresholds worth setting:** CPU sustained >80%, memory sustained >80%, queue depth sustained >50, reporter backlog >0 for more than 15 minutes, file descriptors >80% of limit, subprocesses >50.

## Troubleshooting

| Symptom                                  | Cause                                                                           | Solution                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent stuck in **Pending**               | Registration-key mismatch or network issue                                      | Verify `LUXSWIRL_AUTH_KEY` matches the registration key in Settings; check `docker logs luxswirl_agent`; ensure the agent can reach `https://server.example.com:9000/health`                                                                                                                                                                                                                                                                                                                                                                    |
| API key shows **"Never Used"**           | Approved but not yet authenticated                                              | Wait ~60s for the next heartbeat; check logs for auth errors and a "Saved credentials" message                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Reporter backlog** not clearing        | Server unreachable or slow to process stored reports                            | Verify the server is online/healthy; check server logs and DB insert performance. Backlog drains sequentially at ~100 reports/minute                                                                                                                                                                                                                                                                                                                                                                                                            |
| **N dead-lettered** badge on an agent    | The server refused those report batches as invalid (its 400/422 error envelope) | Check the agent log for the ERROR line "Server refused ... permanently, dead-lettered" (status and the server's error detail); usually the agent and server versions disagree on a field. The batches stay in the agent's `reports/pending_reports.db`, table `dead_letters`, capped at `report_max_dead_letters`                                                                                                                                                                                                                               |
| Performance charts show **no data**      | Agent too old or range too narrow                                               | Agent metrics need version **≥1.0.15**; expand the range (try 24h); wait for the next heartbeat (~60s)                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Agent offline **after key regeneration** | The agent has not fetched its new key yet, or cannot                            | Wait one heartbeat (~60s). Then check the agent log: "The server no longer accepts this agent's key" then "Agent-specific key saved and activated" is a recovery. "Key recovery refused" means `LUXSWIRL_AUTH_KEY` is not an active registration key: set one and restart the agent. "registering again" after "the recovery secret is void" means the key was revoked: approve the new pending agent. "holds no recovery secret" means the agent predates recovery secrets: delete its credentials file, restart it, and approve the new agent |
